# Flutter Web의 React급 화면 품질 검토 및 커뮤니티 IA 교정

검토 대상은 `app.leva.ai.kr`의 Flutter Web 앱이다. 여기서 “React급”은 프레임워크 이름이 아니라
브라우저 제품이 갖춰야 할 정보 구조, 반응형 레이아웃, 상호작용 상태, 타이포그래피, 접근성,
성능과 검증 수준을 뜻한다.

## 결론

Flutter로도 React 기반의 완성도 높은 앱 UI와 같은 수준을 만들 수 있다. 현재 격차의 원인은 Flutter
자체가 아니라 다음 구현 방식이었다.

1. 데스크톱과 모바일이 같은 목적지 목록을 공유해 화면 폭별 정보 구조를 설계할 수 없었다.
2. 커뮤니티의 세 게시판을 페이지 내부 필터로만 취급해, 좌측 내비게이션이 사용자의 현재 위치를
   설명하지 못했다.
3. `/community`의 기본값이 `전체`라서 사용자가 무엇을 보는지 화면 제목과 URL만으로 판단하기
   어려웠다.
4. 시각 개선 계획은 있었지만 운영 화면에서 확인할 명시적 합격 기준과 연결되지 않았다.

React로 재작성할 필요는 없다. `dp_design`의 토큰과 공용 컴포넌트를 유지하면서 화면별 정보 구조와
브라우저 검증 계약을 강화하는 편이 비용과 회귀 위험이 낮다.

## 운영 화면 기준 평가

| 영역 | 배포 전 평가 | 문제 | React급 기준 |
|---|---:|---|---|
| 정보 구조 | D | `커뮤니티` 단일 메뉴 안에 네 개 필터가 숨어 있음 | 데스크톱은 세 게시판을 직접 목적지로 표시 |
| 시각 위계 | C | 화면 제목이 `커뮤니티`라 현재 게시판을 설명하지 못함 | 현재 게시판을 H1과 선택 상태로 동시에 표시 |
| 반응형 | B- | 모바일과 데스크톱의 목적지 모델이 같아 확장에 취약 | desktop/compact 목적지 모델 분리 |
| 상태·피드백 | B | 로딩·빈 상태는 있으나 게시판 맥락이 약함 | 게시판별 설명·행동 문구 유지 |
| 접근성 | B | 공용 Semantics는 있으나 IA 선택 의미가 부족 | 선택된 게시판과 44px 목표를 프로그램적으로 노출 |
| URL·딥링크 | C+ | 필터 URL은 있으나 셸 선택과 브레드크럼이 쿼리를 잃음 | `board`가 레일·H1·브레드크럼의 단일 상태 원천 |
| 시각 일관성 | B | Pretendard·8pt·토큰은 이미 정립 | feature가 임의 스타일을 만들지 않고 공용 토큰 사용 |
| 성능 체감 | 검증 필요 | renderer·초기 자산 기준선이 운영 게이트와 분리됨 | release/profile의 LCP·INP·CLS와 자산 예산 관리 |

배포 전 종합 평가는 **C+**다. 디자인 토큰은 갖춰져 있지만, 내비게이션의 위치 설명과 화면별
우선순위가 그 시스템을 충분히 사용하지 못했다. 이번 변경의 커뮤니티 범위 목표는 **B+**다.
전체 앱을 B+ 이상으로 유지하려면 아래 반복 가능한 방법을 모든 핵심 화면에 적용해야 한다.

## React급 품질을 만드는 방법

### 1. 정보 구조를 상태보다 먼저 설계한다

- 좌측 레일은 제품의 주요 공간과 현재 위치를 설명한다.
- 페이지 내부 세그먼트는 모바일 로컬 내비게이션 또는 보조 필터에만 쓴다.
- 데스크톱과 compact가 같은 목적지 개수를 강제로 공유하지 않는다.
- URL 쿼리, 선택 상태, 화면 제목, 브레드크럼이 같은 값을 사용한다.

### 2. 공용 디자인 시스템을 화면 계약으로 사용한다

- 색은 `DpColors`, 간격은 `DpSpacing`, 타입은 `DpTypography`만 사용한다.
- 제목은 `DpPageHeader`, 목록은 `DpListRow`, 상태는 공용 상태 컴포넌트로 통일한다.
- 카드가 실제 상호작용 단위가 아닐 때는 카드 대신 목록, 구분선, 여백을 쓴다.
- 한 화면에는 하나의 강한 1차 행동만 둔다.

### 3. 반응형을 단순 축소가 아닌 구성 변경으로 구현한다

- desktop: 레일에서 `커뮤니티 → 자유게시판 / Q/A / 피드백`을 직접 노출한다.
- compact: 하단 내비는 네 개 핵심 목적지를 유지하고, 커뮤니티 화면에서 세 게시판을 44px 이상의
  세그먼트로 전환한다.
- 390, 768, 1024, 1440px에서 각각 제목, 검색, 게시판 전환, 글쓰기 행동과 overflow를 검증한다.

### 4. 브라우저 품질을 별도 제품 영역으로 다룬다

- deep link와 새로고침 후에도 같은 게시판이 선택되어야 한다.
- 뒤로가기 기록을 검색 입력 글자마다 오염시키지 않는다.
- hover, focus-visible, pressed, disabled, loading, empty, error를 모두 정의한다.
- release 빌드에서 키보드 순회, 200% 텍스트, reduced motion, 스크린리더 의미를 확인한다.

### 5. 성능을 시각 품질과 같은 릴리스 게이트로 둔다

- `/login`, `/dashboard`, `/path`, `/mentor`, `/community`의 LCP·INP·CLS를 같은 조건에서 기록한다.
- 기본 web 빌드와 wasm 빌드를 브라우저별로 A/B하고 p75 결과로 선택한다.
- Monaco, 광고, 알림과 같은 비필수 자산은 해당 route 또는 동의 이후에 로드한다.
- 초기 전송량과 long task가 기준선보다 5% 이상 나빠지면 릴리스를 막는다.

## 이번 교정의 구현 계약

| 항목 | 변경 |
|---|---|
| 데스크톱 IA | `커뮤니티` 섹션 아래 `자유게시판`, `Q/A`, `피드백` 직접 목적지 |
| 모바일 IA | 기존 네 개 하단 목적지를 유지하고 세 게시판은 화면 상단 로컬 내비게이션으로 제공 |
| 기본 게시판 | `/community`는 `자유게시판`으로 해석 |
| URL | `?board=FREE`, `?board=QNA`, `?board=FEEDBACK` |
| 화면 제목 | `커뮤니티` 고정 제목 대신 현재 게시판 이름 |
| 브레드크럼 | `커뮤니티 → 현재 게시판 → 게시글/작성` |
| 일반 게시글 상세 | `board` 쿼리를 유지해 자유게시판과 피드백의 위치 문맥 보존 |
| 회귀 방지 | desktop/compact 목적지 분리, 선택 index, 기본 게시판, 세 게시판 노출을 위젯 테스트로 고정 |

## 합격 기준

- 데스크톱 좌측 레일에서 커뮤니티 아래 세 게시판이 동시에 보인다.
- 각 항목을 선택하면 URL, 레일 선택, H1, 브레드크럼이 같은 게시판을 표시한다.
- 화면 어디에도 `전체`가 네 번째 주요 게시판처럼 노출되지 않는다.
- 모바일 하단 내비는 네 항목을 유지하며 커뮤니티 안에서 세 게시판을 모두 전환할 수 있다.
- `dart run melos run format`, `analyze`, `test`와 `flutter build web --release`가 통과한다.
- 운영 배포 후 desktop/mobile 캡처와 세 게시판 URL smoke를 남긴다.

## 후속 전체 앱 적용 순서

1. Today와 Path를 “다음 행동 → 완료 조건 → 진행” 순서로 통일한다.
2. 핵심 화면의 loading/empty/error/success/partial 상태를 같은 밀도로 맞춘다.
3. 로그인부터 커뮤니티까지 키보드·focus·deep link 전체 동선을 자동화한다.
4. release/profile 성능 기준선과 renderer A/B를 운영 게이트로 연결한다.
5. 390/768/1024/1440 시각 회귀를 승인된 baseline과 비교한다.

이 문서는 `DESIGN.md`와 `docs/superpowers/plans/2026-09-15-flutter-web-react-grade-design.md`의
원칙을 운영 화면의 합격 기준으로 구체화한다.
