## 1. 캡처 환경에서 배운 것 (다음 세션용)

- **`wait --networkidle`만으로는 이르다.** 목 모드는 실제 네트워크 요청이 없어 networkidle이
  즉시 만족되고 Flutter의 async 로딩은 그 뒤에 끝난다. 마이페이지·설정을 그 상태로 찍으면
  **로딩 스피너만 찍힌다**(처음에 실제로 그렇게 찍혔고, 목 픽스처 부재로 오진할 뻔했다).
  `$B js "new Promise(r => setTimeout(() => r(1), 4000))"`로 명시적으로 기다려야 한다.
- 첫 화면(대시보드)은 앱 부팅 시간이 겹쳐 우연히 충분히 기다려진다 — **첫 캡처만 보고 "정상"이라
  판단하면 안 된다.**
- CanvasKit 렌더라 `$B text`·DOM 기반 분석은 무의미하다(스크린샷만 유효). 릴리스 빌드는
  `debugPrint`가 제거돼 `[MockHttpAdapter] 등록되지 않은 픽스처` 로그도 콘솔에 안 나온다.
- **admin은 `#/auth/callback`으로 직접 이동**하면 `/auth/refresh` 픽스처로 세션이 복원돼 `/dashboard`로 들어간다.
- 다크는 별도 빌드가 필요하고, **재빌드해도 화면이 그대로면 서비스워커 캐시다** — 포트를 바꿔
  새 origin으로 띄우면 우회된다(이번에도 8099→8100→8102→8103으로 갈아탔다).

### 3.1 「다크 레일 분리감」 — 축소 화면 인상이 틀렸고 토큰이 옳았다

캡처를 축소해서 보면 레일과 본문이 거의 같은 톤으로 보여 **처음에 "분리감이 약하다"고 오판했다.**
토큰 실값으로 확인하니 반대였다(`dp_colors.dart` 다크 팔레트):

| 토큰 | 값 | 관계 |
|---|---|---|
| `bg`(본문 배경) | `#0F0E0C` | 가장 어둡다 |
| `surface`(카드) | `#1A1815` | 중간 |
| `railBg`(레일) | `#221E1A` | **가장 밝다** |
| `railBorder` | `#3A342D` | 경계선 |

레일이 본문 배경보다 19단계 밝고 경계선까지 있다 — **Task 3의 목적(레일이 본문과 구별된다)은 달성**이다.
`tagBg #231F1B` / `tagText #A09991` 대비도 약 5.6:1로 4.5:1을 넘는다.

**교훈: 색 판정은 축소된 스크린샷 인상이 아니라 토큰 값으로 한다.**

## 4. 발견 사항

### 4-1 ❌ 셸 밖 화면의 헤더-본문 정렬 어긋남 (신규, 3-A 스펙 §6 목록 밖)

`/diagnostic`(폭 1000)에서 **브랜드 행·페이지 헤더는 좌측 정렬(x≈76)인데 본문은 중앙 정렬**이다
(「실력 진단 15문항」·「진단 시작하기」 버튼이 박스 중앙). 시각 축이 둘로 갈린다.

- 구조: `Center > SingleChildScrollView > ConstrainedBox(maxWidth: readableMaxWidth) >
  Column(crossAxisAlignment: stretch)` 안에 `brandRow` + `DpPageHeader` + 본문(`_StartView`).
  헤더는 stretch + 자체 좌측 패딩(`DpSpacing.lg`)으로 좌측에 붙고, `_StartView`는 자체적으로
  중앙 정렬이라 두 축이 어긋난다.
- **2단계가 `DpPageHeader`를 셸 밖 화면에 도입하면서 생긴 것으로 보인다**(3-A는 이 화면의
  여백만 건드렸다). 같은 구조를 쓰는 `beta_pending`·`consent`도 동일할 가능성이 높다.
- **3-A 스펙 §6의 결함 11건 목록에 없다.** 고치면 셸 밖 4화면 전체에 걸친 범위 확장이 되므로
  이 브랜치에서는 수정하지 않고 보고한다 — **처리 여부는 사용자 판단**이다.

### 4-2 이번 변경과 무관한 사전 존재 동작 (백로그)

- **작성 화면 「게시」 버튼이 콘텐츠 폭을 꽉 채운다.** 1400폭에서 약 1110px. 브랜치 base(`34a0d96`)에서도
  `FilledButton.icon`이 `ListView`(현재 `SliverList.list`)의 직접 자식이라 **전환 이전에도 동일**했다
  (코드 대조 확인). 디자인 의도라는 근거는 문서에 없다.
- **대시보드 「진행률 추이」 차트에 축 라벨이 없다.** 3-B(차트 다중 계열) 범위다.
- **admin 목 모드에 세션 복원 픽스처가 없다.** `/login`에서 더 진행할 수 없어 육안 확인 자체가
  막힌다. 임시 픽스처로 우회했으나(§0) **항구적으로 추가하는 편이 낫다**.

### 4-3 확인하지 못한 항목 (정직한 미완 보고)

| 항목 | 사유 |
|---|---|
| `login`·`beta-pending`·`consent` 3화면 | 목 `POST /auth/refresh`가 **항상 인증에 성공**해 `/login`으로 가도 곧바로 리다이렉트된다. 각 화면을 보려면 픽스처를 화면마다 다르게 조작하고 매번 재빌드해야 한다(빌드 1회 약 1분). **Task 14-4(`beta_pending` 여백 토큰화)는 값이 완전히 같아 시각 변화가 0이므로**(16→`lg`=16, 24→`xl`=24) 육안 확인의 실익이 없다고 판단해 생략했다 |
| admin 필터의 **줄바꿈** | 운영 필터가 4개(미처리·처리됨·기각됨·전체)뿐이라 합계 폭이 약 292px다. **520폭에서도 한 줄**이라 어떤 지원 폭에서도 다중 런이 생기지 않는다 — Task 12의 「admin 대시보드는 스크롤이 안 생긴다」와 같은 성격이다. **오버플로가 없다는 것은 확인**했으나 `Wrap`의 다중 런 렌더는 육안으로 확인 불가 |
| admin 4화면 필터 **간격 동일성** | `reports`만 필터를 가진다(`users`·`ads`·`support`는 `DpDataTable` 뷰포트 고정형). 비교 대상이 없다 |

## 6. 결론

3-A가 바꾼 것 중 **육안으로 확인 가능한 항목은 전부 의도대로 렌더된다.** 2단계처럼 green 상태에서
숨어 있던 레이아웃 결함은 이번 변경분에서 발견되지 않았다.

다만 **셸 밖 화면의 정렬 어긋남(§4-1)** 이 새로 드러났다. 3-A 범위 밖이라 이 브랜치에서 고치지
않았고, 처리 여부는 사용자 판단이다.
